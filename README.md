# CUMCM 2026 - 数学建模竞赛仓库

本项目为 2026 年全国大学生数学建模竞赛（CUMCM）团队代码、论文及支撑材料协作仓库。
团队由 3 名成员共同协作与维护。

---

## 📁 推荐目录结构

```text
数模2026/
├── CUMCM_LaTeX_Structure_Template/   # 论文 LaTeX 模板与各章节源文件
├── data/                             # 题目数据与预处理结果（建议控制文件体积）
├── src/                              # 核心建模与算法代码 (Python / MATLAB 等)
│   ├── q1/                           # 问题一相关脚本
│   ├── q2/                           # 问题二相关脚本
│   ├── q3/                           # 问题三相关脚本
│   └── utils/                        # 通用绘图、数据清洗等辅助函数
├── docs/                             # 赛题通知、参考论文与文献资料
├── .gitignore                        # Git 忽略规则（LaTeX 编译缓存、Python 缓存等）
└── README.md                         # 仓库说明与三人协作准则
```

## 🤝 三人协作准则 (Git & 比赛规范)

数学建模竞赛赛期紧凑（通常仅 72~84 小时），为避免代码丢失、版本覆盖和合并冲突，3 位队员请共同遵守以下准则：

### 1. 分工与分支策略 (Branch & Workflow)
* **`main` 主分支保护**：`main` 分支始终保持为**稳定版本**（即代码能跑通、论文能正常编译通过）。
* **开分支协作**：队员开发具体模块时，从 `main` 切出子分支，例如：
  * `feat/q1-data`（问题一数据预处理）
  * `feat/q2-algorithm`（问题二算法求解）
  * `docs/paper-sec6`（论文模型求解章节撰写）
* **日常同步习惯**：
  * **开工前**：先 `git pull origin main`，获取队友最新进展。
  * **完工后**：确认本地能正常运行/编译，再提交并提 PR/合并至 `main`。

### 2. LaTeX 论文防冲突指南 (非常重要)
* **严禁多人同时修改 `main.tex`**：论文主干已拆分至 `sections/` 目录下（如 `01_problem_restatement.tex`、`06_model_establishment_and_solution.tex` 等），每个人仅编辑自己负责的章节小文件。
* **插图统一存放**：所有论文用图导出为高分辨率 PNG/PDF 后放入 `figures/` 文件夹，按 `fig_q1_flowchart.png`、`fig_q2_loss.png` 规范命名。
* **不要提交编译过程文件**：如 `.aux`、`.log`、`.synctex.gz` 等已配置在 `.gitignore` 中，请勿使用 `git add -f` 强制提交。

### 3. 代码规范与数据管理
* **固定随机数种子 (Seed)**：涉及随机算法（蒙特卡洛、模拟退火、遗传算法、深度学习等），务必显式设定种子（如 `np.random.seed(42)`），确保结果可复现。
* **大文件不入库**：单文件超过 50MB 的大型数据集，请使用局域网传输或云盘共享，仓库内仅保留处理脚本或轻量级样本数据（避免 Git 仓库臃肿推送超时）。
* **Jupyter Notebook 提交前清空输出**：若使用 `.ipynb`，提交前请执行 `Clear All Outputs`，避免因画图数据 base64 嵌入导致巨大的 merge 冲突。
* **依赖环境声明**：新增 Python 第三方库时，及时在根目录同步更新 `requirements.txt`。

### 4. Commit 提交规范
提交信息简洁明了，采用常见前缀方便追溯：
* `feat: 完成问题一灰色预测模型求解`
* `fix: 修正问题二目标函数约束条件`
* `docs: 更新论文第二节问题分析内容`
* `style: 优化图表配色与字体排版`

### 5. 比赛时间线与封版纪律
* **前 48 小时（攻坚期）**：高频推送各自模块的分支或成果，群内保持沟通。
* **最后 12 小时（集成期）**：代码全面冻结，仅允许修复致命 bug。
* **最后 4 小时（封版期）**：全部内容合并至 `main`，由论文负责人统一在本地进行最终完整编译，核对页码、支撑材料清单与格式要求，生成最终提交文件。
